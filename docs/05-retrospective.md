# 05 项目复盘与下一步

## 1. 我的项目推进方式

我选择第 1 题后，先确定使用 Python 和 CLI 完成可运行的核心链路，再按数据结构、业务工具、Agent 循环、存储、Trace、测试案例和交付文档逐步推进。开发过程中我持续核对“当前完成什么、下一步做什么”，并根据执行耗时把策略调整为先完成核心实现、再集中做完整回归测试。

我重点关注的不只是功能能否运行，还包括题目明确要求的动态决策、时段冲突后的确认边界、重复提交、防止虚报保存成功、工具失败和真实模型 Live Trace。项目后期，我进一步检查 AI 使用说明和交付文档，确保最终仓库既完整，又如实说明个人贡献与 AI 辅助范围。

## 2. 最难的问题与我的理解

### 2.1 动态决策与确定性安全边界

题目要求模型观察工具结果后改变动作，但不能让模型自行决定权限和事实。项目最终把职责分成两层：模型负责选择下一步工具，确定性代码负责工具白名单、参数校验、调用上限和最终事实审计。

我认为这一取舍是本项目的核心：既能体现 ReAct 动态决策，又不能仅靠提示词防止越权、伪造草稿或虚报保存成功。

### 2.2 替代时段与用户确认

18:00 被占用后找到 19:00，并不代表用户已经同意改到 19:00。项目将候选时段标记为 `pending_confirmation`，最终任务状态为 `awaiting_confirmation`。这一边界同时由 Schema、保存工具、结果审计和测试保护。

这让我进一步明确：Agent 给出建议和 Agent 获得业务授权是两件不同的事，不能因为模型“认为合理”就改变用户的硬性要求。

### 2.3 重复提交与事实一致性

如果只使用 `request_id` 去重，同一个业务请求换一个请求 ID 就会重复保存。项目使用规范化业务字段生成幂等键，并在锁内检查已有草稿。最终输出还必须和工具观察一致，模型不能自行声称保存成功。

我将幂等、防重复和保存事实核对视为本题的重要得分点，而不是普通的附加功能。

### 2.4 Mock 与真实模型证据

Offline Mock 能稳定复现六个必须验收场景，并补充人工确认与提示词注入两条安全路径，适合自动化测试，但它的动作是预设实现，不能证明真实模型会根据工具结果正确调整下一步。因此，Mock Trace 与 Live Trace 必须明确区分。本项目最终使用DeepSeek `deepseek-flash`补充正常、冲突和规则阻断三条真实模型运行记录。

首次Live运行暴露出两个Mock未发现的问题：模型最终文本不是严格JSON，以及冲突路径找到候选时段后漏掉草稿保存。项目没有修改失败Trace冒充成功，而是根据真实结果补充最终JSON模板、冲突路径动作约束和DeepSeek兼容处理，再次运行后通过。这说明Live验证不仅是交付材料，也是发现模型适配问题的重要手段。

## 3. 当前收获

- Agent 项目的重点不只是生成文本，而是动作选择、工具事实、状态流转、权限边界和可审计性；
- 业务阻断、信息不足、工具故障和达到调用上限应有不同状态，不能统一当作“失败后重试”；
- 最终结果不能只信任模型自述，需要用工具观察做事实一致性校验；
- Trace 应记录动作、参数、返回摘要和下一步依据，不应记录模型隐藏思维过程；
- 候选时段必须等待用户确认，保存草稿不能被描述为已经发布；
- AI 可以加快实现和测试，但候选人仍需亲自理解核心代码、运行验证并对交付内容负责。

优先级从高到低：

1. 运行多组真实模型案例，统计动作正确率、工具调用次数、延迟和费用；
2. 根据 Live Trace 暴露的问题调整系统提示和工具描述；
3. 实现用户确认后更新原草稿的流程；
4. 将 JSON 文件存储替换为 SQLite 事务存储；
5. 增加规则版本、草稿版本和审计版本号；
6. 增加 HTTP API 和人工审批接口；
7. 使用匿名化业务数据扩充脏数据和边界测试。
